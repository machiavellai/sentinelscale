# SentinelScale — Study Guide
_Generated by Claude Code `/study` command_

## What This Project Does

SentinelScale is a media ingestion and processing server: clients POST an image or video, receive a job ticket (202 Accepted) immediately, and subscribe via Socket.io for real-time progress as the file is processed asynchronously across worker threads. It's built for systems that need to ingest media at scale without blocking the HTTP layer — the API stays fast while BullMQ + Redis provides durability and Piscina provides true CPU parallelism.

**A film processing lab.**

Customers drop off film rolls at the front desk, get a ticket number, and leave. The desk clerk checks if the lab is at capacity before accepting new rolls. Technicians in the back pull from the inbox, route portrait film to the portrait lab and movie reels to the video suite, and call out progress over the intercom whenever a batch step completes.

## The Flow in Plain English

A client POSTs a video to `/api/upload`. The route checks queue depth — if over `MAX_QUEUE_SIZE`, it 503s. Otherwise it generates a UUID, fires busboy to stream the file bytes directly to `uploads/<jobId>.mp4` on disk (never buffering in RAM), collects processing options from other form fields, enqueues a BullMQ job, and returns 202 with the jobId.

The BullMQ worker (concurrency 5) picks the job off Redis, reads the file, and routes it: images go to the image Piscina pool (with the bytes transferred via SharedArrayBuffer to avoid copying), videos go to the video pool (path only). The pool dispatches to a free worker thread running FFmpeg or Sharp. Progress is reported via `job.updateProgress()`. When done the temp file is deleted and the result resolves. Any Socket.io client subscribed to that jobId's room receives the progress events in real time.

## The 5 Files That Run This Project

### 1. `src/routes/upload.route.js`
**What it does:** Receives the multipart upload, enforces backpressure, streams the file to disk, enqueues the job.
**Why it matters:** The only public surface. Get this wrong and you buffer 500MB files in RAM or miss the backpressure check.
**What to notice:** `req.pipe(bb)` — the request is a stream, not `req.body`. The job isn't enqueued until the `'finish'` event fires (file fully on disk). The `{ jobId }` option on `ingestionQueue.add()` makes BullMQ use your UUID as job ID, which is what ties it to the Socket.io room.

### 2. `src/queues/ingestion.worker.js`
**What it does:** BullMQ coordinator — pulls jobs from Redis, reads the file, routes to the right Piscina pool, emits progress, cleans up.
**Why it matters:** This is the routing layer, NOT the processing layer. Confusing it with the Piscina workers in `src/workers/` breaks your mental model of the two-layer architecture.
**What to notice:** `concurrency: 5` means BullMQ calls the processor function 5 times in parallel. The image path creates a `SharedArrayBuffer`; the video path passes only the file path string.

### 3. `src/workers/pool.js`
**What it does:** Creates and exports two Piscina thread pools — imagePool (full CPU count) and videoPool (half CPU count).
**Why it matters:** This is the resource allocation decision. Without two pools, slow video transcodes would starve all image jobs.
**What to notice:** `videoPool` gets `Math.floor(maxThreads / 2)` threads with a longer idle timeout (60s vs 30s) because FFmpeg startup is expensive.

### 4. `src/utils/sharedBuffer.js`
**What it does:** Copies a Node Buffer into a SharedArrayBuffer with an Atomics spinlock so threads can read image data without serialization.
**Why it matters:** Eliminates hundreds of MB of copy overhead at high concurrency. A 50MB image × 5 concurrent workers = 250MB wasted if serialized normally.
**What to notice:** `Atomics.compareExchange(lock, 0, 0, 1)` is the compare-and-swap that forms the spinlock. The lock is held only for the duration of `Buffer.from(new Uint8Array(sab))` — microseconds.

### 5. `src/queues/ingestion.queue.js`
**What it does:** Declares the BullMQ queue with retry policy (3 attempts, exponential backoff) and job retention limits.
**Why it matters:** Every job's durability guarantees are set here. The `maxRetriesPerRequest: null` in `RedisConfig.js` is a BullMQ requirement — without it BullMQ throws on startup.
**What to notice:** `removeOnComplete: { count: 100 }` and `removeOnFail: { count: 500 }` — without these, Redis accumulates every job record forever.

## Key Patterns & Concepts

### 1. Backpressure Gate
**Analogy:** ER triage nurse who checks current patient load before admitting anyone new.
**Location:** `src/routes/upload.route.js:16-23`
**Consequence:** Server degrades gracefully under load — clean 503s instead of Redis memory exhaustion. Callers must handle 503 and retry.

### 2. Zero-Copy SharedArrayBuffer Transfer
**Analogy:** Putting one original document on the table instead of photocopying it for everyone in the meeting.
**Location:** `src/utils/sharedBuffer.js`, called in `src/queues/ingestion.worker.js:22-23`
**Consequence:** Eliminates serialization overhead for large images. Requires Node ≥18 and careful spinlock coordination.

### 3. Dual-Pool Worker Isolation
**Analogy:** Hospital with separate ICU and general ward staffing — a surge in one can't cannibalize the other.
**Location:** `src/workers/pool.js`
**Consequence:** Video transcodes can never starve image jobs. Cost: two thread pools at startup.

### 4. Two-Layer Worker Architecture
**Analogy:** Factory floor supervisor (BullMQ worker) who routes orders to specialist machinists (Piscina workers).
**Location:** `src/queues/ingestion.worker.js` (coordinator) vs `src/workers/*.worker.js` (CPU workers)
**Consequence:** Clean separation — BullMQ owns durability/retry, Piscina owns CPU parallelism. The common confusion: two directories both contain `.worker.js` files that do fundamentally different things.

### 5. Accept-Then-Process (202 Pattern)
**Analogy:** Dry cleaner that gives you a receipt immediately and texts you when clothes are ready.
**Location:** `src/routes/upload.route.js:80-83` (202 response) + `src/sockets/progress.socket.js` (the callback — not yet built)
**Consequence:** HTTP throughput decoupled from processing throughput. Clients must implement a second channel (Socket.io) which adds complexity.

## Glossary

| Term | Definition |
|---|---|
| **BullMQ** | Job queue library using Redis as its durable storage and pub/sub backend |
| **Piscina** | Node.js worker thread pool manager — runs JS files in true OS threads |
| **busboy** | Streaming multipart/form-data parser — processes files as a stream, never buffers |
| **SharedArrayBuffer (SAB)** | Memory accessible by multiple JS threads simultaneously without copying |
| **Atomics** | Built-in JS primitives for thread-safe operations on SharedArrayBuffers |
| **Spinlock** | A lock that busy-waits in a loop until it can acquire access |
| **ingestion worker** | The BullMQ coordinator in `src/queues/` — routes jobs, does not process them |
| **image/video worker** | The Piscina CPU workers in `src/workers/` — actual Sharp/FFmpeg execution |
| **QueueEvents** | BullMQ's cross-process event emitter backed by Redis pub/sub |
| **jobId** | UUID serving triple duty: BullMQ job ID, upload filename on disk, Socket.io room name |
| **backpressure** | Refusing new work when queue is too deep to prevent Redis memory exhaustion |
| **concurrency** | How many BullMQ jobs the single worker processes simultaneously (currently 5) |
| **maxRetriesPerRequest: null** | ioredis setting required by BullMQ — without it BullMQ throws on startup |

## Open Questions

1. **`server.js` is missing two wires:** `require('./queues/ingestion.worker')` (without it jobs sit in Redis forever) and `initProgressSocket(io)` (Socket.io progress bridge). The file `src/sockets/progress.socket.js` also doesn't exist yet.

2. **Import casing mismatch:** `ingestion.queue.js` imports `'../config/RedisConfig'` but `ingestion.worker.js` imports `'../config/redis'`. Windows masks this; Linux/Docker will throw `MODULE_NOT_FOUND` on the worker.

3. **Wasted `readFileSync` on video path:** `ingestion.worker.js` reads the entire file into a Buffer for every job, but the video path only uses the file path string — the Buffer is never consumed for video jobs.

4. **`piscina`, `sharp`, and `fluent-ffmpeg` are absent from `package.json`:** A fresh `npm install` will not install them. They must be added manually.
