## What This Project Does

SentinelScale is a media ingestion and processing server. Clients POST an image or video, receive a job ticket (202 Accepted) immediately, and subscribe via Socket.io for real-time progress as the file is processed asynchronously across worker threads. It is built for systems that need to ingest media at scale without blocking the HTTP layer — the API stays fast while BullMQ + Redis provides durability and Piscina provides true CPU parallelism. Processed output files land in the `processed/` directory at the project root.

## The Flow in Plain English

You POST a video to `/api/upload`. The route checks queue depth — if over `MAX_QUEUE_SIZE` it returns 503. Otherwise it generates a UUID (the jobId), fires busboy to stream the file bytes directly to `uploads/<jobId>.mp4` on disk (never buffering in RAM), collects processing options from other form fields, enqueues a BullMQ job, and returns 202 with the jobId.

The BullMQ worker (concurrency 5) picks the job off Redis, routes it: images go to the image Piscina pool (bytes transferred via SharedArrayBuffer to avoid copying), videos go to the video pool (file path only). The pool dispatches to a free worker thread running Sharp or FFmpeg. Progress is reported via `job.updateProgress()`. When done, the output is written to `processed/<jobId>.<format>`, the original upload is deleted, and a "completed" event fires through Redis. The progress socket picks it up and pushes it to any Socket.io client subscribed to that jobId's room.

## The 5 Files That Run This Project

### 1. `src/routes/upload.route.js`
**What it does:** Receives the multipart upload, enforces backpressure, streams to disk, enqueues the job.
**Why it matters:** The only public surface. Get this wrong and you buffer 500MB files in RAM or accept jobs when the system is overwhelmed.
**What to notice:** `req.pipe(bb)` — the request is a stream, not `req.body`. The job isn't enqueued until the `'finish'` event fires (file fully on disk). The `{ jobId }` option on `ingestionQueue.add()` makes BullMQ use your UUID as the explicit job ID — same ID ties the file, the queue job, and the Socket.io room together.

### 2. `src/queues/ingestion.worker.js`
**What it does:** BullMQ coordinator — pulls jobs from Redis, routes to the right Piscina pool, saves output to `processed/`, cleans up.
**Why it matters:** This is the routing layer, NOT the processing layer. The Piscina workers in `src/workers/` do the CPU work. Confusing the two layers breaks the mental model of the two-layer architecture.
**What to notice:** For images, it writes the returned buffer to `processed/<jobId>.webp` and stores only the path in Redis (not the raw bytes). For videos, it pre-constructs the output path and passes it to the thread. At the end, `fs.unlink(filePath)` removes the original upload — this is why `uploads/` is empty after processing.

### 3. `src/workers/pool.js`
**What it does:** Creates and exports two Piscina thread pools — imagePool (full CPU count) and videoPool (half CPU count).
**Why it matters:** Two separate pools mean video transcodes can never starve image jobs. Without isolation, one long video job would block everything.
**What to notice:** `videoPool` gets `Math.floor(maxThreads / 2)` threads and a 70s idle timeout (FFmpeg startup is expensive, keep threads alive longer). imagePool gets the full thread count with 30s idle timeout.

### 4. `src/utils/sharedBuffer.js`
**What it does:** Copies a Node Buffer into a SharedArrayBuffer with an Atomics spinlock so image worker threads can read it without serialization overhead.
**Why it matters:** Eliminates copy overhead. A 50MB image × 5 concurrent workers = 250MB wasted if serialized normally through JSON.
**What to notice:** `Atomics.compareExchange(lock, 0, 0, 1)` is the compare-and-swap that forms the spinlock. The lock is held only for the microseconds it takes to copy `Buffer.from(new Uint8Array(sab))`. Requires Node ≥ 18.

### 5. `src/sockets/progress.socket.js`
**What it does:** Bridges BullMQ's Redis pub/sub job events to connected Socket.io clients.
**Why it matters:** Without this file, clients subscribe to rooms that nobody ever emits to. The 202 pattern is broken at the second channel — jobs complete invisibly.
**What to notice:** Uses BullMQ's `QueueEvents` class which subscribes to Redis pub/sub (not directly to the worker). This means progress events flow correctly even when the HTTP server and worker run on different machines.

## Key Patterns & Concepts

### 1. The 202 Pattern — Accept Now, Process Later
**Analogy:** FedEx drop-off. They take your package immediately and give you a tracking number. You don't wait while they sort it — you check tracking later.
**Location:** `upload.route.js` (the 202 response) + `progress.socket.js` (the callback channel)
**Consequence:** HTTP throughput is decoupled from processing throughput. Clients must implement two connections (HTTP + Socket.io) which adds complexity, but the server never blocks.

### 2. Two-Layer Worker Architecture
**Analogy:** Head waiter (BullMQ worker) routes orders to kitchen stations (Piscina workers). They have completely separate jobs.
**Location:** `src/queues/ingestion.worker.js` (coordinator) vs `src/workers/*.worker.js` (CPU executors)
**Consequence:** BullMQ owns durability and retry. Piscina owns CPU parallelism. Common confusion: both directories have `.worker.js` files that do fundamentally different things.

### 3. Zero-Copy SharedArrayBuffer Transfer
**Analogy:** Putting one original document on the table for everyone to read, instead of photocopying it for each person.
**Location:** `src/utils/sharedBuffer.js`, called in `src/queues/ingestion.worker.js`
**Consequence:** Eliminates serialization overhead for large images. Requires a spinlock (Atomics) to coordinate thread access safely.

### 4. Backpressure Gate
**Analogy:** A nightclub bouncer counting how many people are inside. At capacity, new people wait outside instead of causing a dangerous crush.
**Location:** `src/routes/upload.route.js` — `getWaitingCount()` check at the top of the upload handler
**Consequence:** Server degrades gracefully under load with clean 503s instead of Redis memory exhaustion. Callers must handle 503 and retry.

### 5. One jobId Rules Everything
**Analogy:** A restaurant order number that is also your table number and your receipt — one ID for all three.
**Location:** Generated in `upload.route.js`, used in `ingestion.queue.js`, `ingestion.worker.js`, and `progress.socket.js`
**Consequence:** No lookup table needed. The filename on disk, the BullMQ job ID, and the Socket.io room name are all identical.

## Glossary

| Term | Plain English definition |
|---|---|
| **BullMQ** | A job queue — a to-do list stored in Redis so it survives restarts and can retry failed tasks |
| **Piscina** | A thread pool manager — spins up real parallel OS threads so Node can use multiple CPU cores |
| **busboy** | A file stream parser — reads uploads piece by piece instead of loading the whole file into memory |
| **SharedArrayBuffer (SAB)** | A block of memory that multiple threads can read simultaneously without copying |
| **Atomics / Spinlock** | A safety mechanism — makes threads take turns accessing shared memory so they don't corrupt each other |
| **QueueEvents** | BullMQ's cross-process event listener — subscribes to Redis pub/sub for job progress/completed/failed events |
| **ingestion worker** | The BullMQ coordinator in `src/queues/` — routes jobs, does no CPU processing itself |
| **image/video worker** | The Piscina CPU workers in `src/workers/` — actual Sharp/FFmpeg execution in OS threads |
| **jobId** | A UUID that serves as the upload filename, the BullMQ job ID, and the Socket.io room name simultaneously |
| **backpressure** | Refusing new work (503) when the queue is too deep to prevent system overload |
| **202 Accepted** | HTTP status meaning "got it, working on it, check back later" — foundation of async upload pattern |
| **ffmpeg-static** | npm package that bundles a pre-compiled ffmpeg.exe inside node_modules — no system PATH dependency |
| **PROCESSED_DIR** | The `processed/` folder at project root — where all finished output files land after processing |
| **concurrency: 5** | BullMQ setting — how many jobs the single worker processes simultaneously |
| **maxRetriesPerRequest: null** | ioredis setting required by BullMQ — without it BullMQ throws on startup |

## Open Questions / Next Steps

1. **No download endpoint yet** — processed files exist at `processed/<jobId>.<ext>` but there's no `GET /api/result/:jobId` route to serve them. A client receiving `job:completed` gets an `outputPath` on the server's filesystem — useless from a browser.
2. **No authentication** — any client can upload anything. No API key, no rate limiting beyond the queue depth check.
3. **`processed/` is never cleaned up** — output files accumulate indefinitely. A cleanup job (cron or TTL) is needed for production.
4. **Image output buffer still returned to coordinator** — the image worker returns `data` (raw buffer) to the BullMQ coordinator which then writes to disk. This means the buffer crosses the Piscina→BullMQ boundary. For very large images consider having the image worker write to disk directly given an `outputPath` (same pattern as video).
